# HTTP Request Smuggling — Checklist de identificación y explotación (BSCP)

> Apuntes de referencia rápida: qué payload lanzar para saber ante qué variante estás, y qué hacer con cada una una vez confirmada.

---

## 0. Idea clave antes de nada

Todo esto gira en torno a **quién manda en la longitud del request**: el front-end (proxy/balanceador) y el back-end (servidor de aplicación) tienen que estar de acuerdo en dónde termina una petición y empieza la siguiente. Si usan mecanismos distintos (`Content-Length` vs `Transfer-Encoding`, o incluso si uno de los dos **ignora** ambos), puedes desincronizarlos.

Nomenclatura `X.Y`: **X = qué usa el front-end**, **Y = qué usa el back-end**.

| Nombre      | Front-end usa                                             | Back-end usa                                             |
| ----------- | --------------------------------------------------------- | -------------------------------------------------------- |
| CL.TE       | Content-Length                                            | Transfer-Encoding                                        |
| TE.CL       | Transfer-Encoding                                         | Content-Length                                           |
| TE.TE       | TE (pero uno de los dos se puede "cegar" con obfuscación) | TE                                                       |
| H2.CL       | Longitud implícita HTTP/2                                 | Content-Length (tras downgrade a HTTP/1)                 |
| H2.TE       | Longitud implícita HTTP/2                                 | Transfer-Encoding (tras downgrade)                       |
| CL.0 / H2.0 | Content-Length (o longitud implícita H2)                  | Ignora el body (lo trata como si Content-Length fuese 0) |
| 0.CL        | Front-end ignora Content-Length                           | Back-end sí lo procesa                                   |

**Antes de nada con HTTP/2:** Burp por defecto habla HTTP/2 si el sitio lo anuncia por ALPN. Para los ataques clásicos (CL.TE/TE.CL/TE.TE) necesitas forzar HTTP/1.1 manualmente desde _Inspector → Request attributes → Protocol_ en Repeater.

---

## 1. Orden recomendado de pruebas (triage)

1. **CL.TE** (timing) — es el menos disruptivo para otros usuarios, pruébalo primero.
2. **TE.CL** (timing) — solo si el anterior no dio nada. Este sí puede afectar a otras peticiones en curso si el sitio fuese CL.TE, así que ve con cuidado.
3. Si ninguno responde y hay `Transfer-Encoding` de por medio → prueba variantes **TE.TE** (obfuscación del header).
4. Si el sitio usa HTTP/2 de cara al cliente → prueba **H2.CL** y **H2.TE** (con downgrade).
5. Si nada de lo anterior funciona pero sospechas desync → prueba **CL.0** (sin tocar ningún header, solo con Content-Length "normal").
6. Casos más avanzados / mystery labs difíciles → **0.CL**, **request tunnelling**, **response queue poisoning**, **client-side desync**.

---

## 2. HTTP/1.1 — Detección por _timing_ (fase de descubrimiento)

Envía la petición y mide si el servidor tarda en responder (~timeout, no responde hasta que Burp corta la conexión). Un delay = candidato fuerte.

### 2.1 CL.TE — payload de timing

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 4

1
A
X
```

**Por qué funciona:** el front-end usa `Content-Length: 4`, así que reenvía solo `1\r\nA\r\n` (4 bytes) y se come la `X`. El back-end usa `Transfer-Encoding`, procesa el chunk `1` (1 byte = `A`) y se queda esperando el siguiente chunk → **timeout**.

### 2.2 TE.CL — payload de timing

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Transfer-Encoding: chunked
Content-Length: 6

0

X
```

**Por qué funciona:** el front-end usa `Transfer-Encoding`, ve el chunk `0` como fin de mensaje y reenvía solo hasta ahí, dejando la `X` fuera. El back-end usa `Content-Length: 6`, espera 6 bytes de body y se queda esperando el resto → **timeout**.

⚠️ Nota de la propia PortSwigger: el test de TE.CL es más "ruidoso" — si el sitio en realidad es CL.TE, este test puede desincronizar a otro usuario real. Por eso va en segundo lugar.

---

## 3. HTTP/1.1 — Confirmación por _respuesta diferencial_

Una vez tienes un candidato por timing, confírmalo demostrando que puedes "contaminar" la siguiente petición. Se manda en **dos conexiones distintas** (o secuencia en Repeater con "send group in sequence, single connection"):

1. Un request **"ataque"** que deja un prefijo colgando.
2. Un request **"normal"** inmediatamente después, que debería recibir una respuesta rara (404, contenido ajeno, etc.) si el ataque tuvo éxito.

### 3.1 Confirmar CL.TE

```http
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 49
Transfer-Encoding: chunked

e
q=smuggling&x=
0

GET /404 HTTP/1.1
Foo: x
```

Si el back-end queda "enganchado" a `GET /404...`, tu siguiente request normal (a `/search`) llegará con esa cabecera pegada delante y el servidor responderá **404** en vez de 200.

### 3.2 Confirmar TE.CL

```http
POST /search HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 4
Transfer-Encoding: chunked

7c
GET /404 HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 144

x=
0
```

En Burp Repeater: desmarca **"Update Content-Length"** en el menú de Repeater, y no olvides el `\r\n\r\n` final tras el último `0`.

**Reglas de oro para que esta fase no te dé falsos negativos:**

- Ataque y request normal → **misma URL y mismos parámetros** (muchos backends enrutan por ruta).
- Usa **conexiones diferentes** para cada uno.
- Puede haber "carrera" con tráfico real de otros usuarios: si el 404 no llega, reintenta.
- Si afectas a otro usuario real por error, para — puedes estar causando impacto no controlado.

## 4. TE.TE — cuando ambos "entienden" TE pero uno se puede cegar

Si ninguno de los dos tests anteriores da timing, pero sospechas que **ambos** servidores soportan `Transfer-Encoding`, intenta ofuscar la cabecera para que solo uno de los dos la reconozca. Si lo consigues, el ataque resultante se comporta como CL.TE o TE.CL según a cuál "cegaste".

Prueba estas variantes (una por una) sustituyendo la cabecera `Transfer-Encoding: chunked` normal:

```
Transfer-Encoding: xchunked

Transfer-Encoding : chunked

Transfer-Encoding: chunked
Transfer-Encoding: x

Transfer-Encoding:[tab]chunked

 Transfer-Encoding: chunked      (espacio delante del nombre de la cabecera)

X: X[\n]Transfer-Encoding: chunked

Transfer-Encoding
: chunked
```

Estas mismas técnicas de ofuscación son útiles también para provocar comportamiento **CL.0** en la fase de "eliciting" (ver §7).

## 5. HTTP/2 — H2.CL y H2.TE (por _downgrade_)

HTTP/2 puro, extremo a extremo, es inmune a smuggling (la longitud va en los frames, sin ambigüedad). El problema aparece cuando el front-end habla HTTP/2 con el cliente pero reescribe la petición a HTTP/1 para el back-end (**downgrading**).

### 5.1 H2.CL

El front-end puede reutilizar un header `content-length` inyectado en la petición HTTP/2 al generar el request HTTP/1, aunque no coincida con la longitud real del mensaje.

```
:method   POST
:path     /example
:authority vulnerable-website.com
content-type application/x-www-form-urlencoded
content-length 0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Content-Length: 10

x=1
```

Front-end (H2) usa su mecanismo de longitud interno y reenvía todo. Back-end (H1) usa el `Content-Length: 0` inyectado → cree que el body ya terminó, y trata `GET /admin...` como el inicio del siguiente request.

💡 _Tip práctico:_ añade un `Content-Length` ligeramente mayor que tu body en el prefijo smuggleado, para que la petición de la víctima se "pegue" detrás pero se trunque antes de sus cabeceras (evita errores de cabecera duplicada).

### 5.2 H2.TE

Chunked encoding no debería existir en HTTP/2 (el spec dice que hay que stripearlo o rechazar el request). Si el front-end no lo hace y downgradea a un back-end HTTP/1 que sí soporta chunked:

```
:method   POST
:path     /example
:authority vulnerable-website.com
content-type application/x-www-form-urlencoded
transfer-encoding chunked

0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Foo: bar
```

**Cómo probarlo en Burp:** fuerza el protocolo a HTTP/2 en el Inspector aunque el sitio no lo anuncie (Settings → Tools → Repeater → "Allow HTTP/2 ALPN override"), por si hay soporte H2 oculto que se te esté pasando.

Si confirmas H2.CL o H2.TE, puedes explotarlo con **las mismas técnicas clásicas** de la sección 6 (bypass de controles, captura de requests, etc.), solo que el vector de entrada es HTTP/2.

## 6. Qué explotar según el tipo detectado (CL.TE / TE.CL / TE.TE / H2.CL / H2.TE)

Esta es la parte que sueles preguntarte: **una vez confirmas el desync, ¿qué hago con él?** El payload smuggleado (lo que va después del `0\r\n\r\n` o del chunk terminador) es literalmente el siguiente request que el back-end procesará como si viniera "limpio" — ahí está toda la magia.

|Objetivo|Idea del ataque|Qué necesitas|
|---|---|---|
|**Bypass de controles del front-end**|Smugglea `GET /admin HTTP/1.1` con un `Host: localhost` (o el header que use el control de acceso) para que el back-end lo trate como tráfico interno/confiable|Front-end que bloquea `/admin` por ruta o IP; back-end que confía ciegamente en lo que le llega|
|**Revelar reescritura del front-end**|Smugglea un request y deja que la siguiente petición (con headers reales del front-end, ej. `X-Forwarded-For`, `X-Forwarded-Proto`) se "pegue" detrás — así ves exactamente qué cabeceras añade el front-end|Cualquier endpoint que refleje headers en la respuesta|
|**Bypass de autenticación de cliente (mTLS / certificados)**|Igual que el bypass de controles, pero inyectando cabeceras tipo `X-SSL-CLIENT-CN: administrator` que el front-end normalmente añadiría tras validar el certificado|Back-end que confía en headers "internos" sin volver a validarlos|
|**Capturar requests de otros usuarios**|Smugglea una petición a un endpoint que **almacene** datos que luego puedas leer (comentarios, feedback, logs visibles). El siguiente usuario real que llegue verá su petición "atrapada" como el body de tu request|Alguna funcionalidad de guardado/reflejo de texto libre|
|**Explotar un XSS reflejado "normalmente inalcanzable"** (WAF, bots, restricciones de red)|Smugglea el payload XSS como si fuera la petición de la víctima; el navegador de la víctima real recibe la respuesta con el payload inyectado|Un XSS reflejado que normalmente no puedes disparar tú mismo (p. ej. solo accesible desde una red interna, o filtrado por WAF en la ruta normal)|
|**Convertir una redirección on-site en open redirect**|Si hay una ruta que redirige y usa el header `Host` para construir la URL, smugglea un `Host` distinto y deja que la víctima siga la redirección hacia un dominio externo|Redirecciones root-relative que confían en `Host`|
|**Web cache poisoning**|Smugglea una petición cuya respuesta el sistema de caché guarde asociada a una URL "normal" (ej. un `.js` estático) — la respuesta envenenada se sirve a todos los usuarios que pidan esa URL|Cache delante o integrado en el back-end, clave de caché que no incluye lo que smuggleas|
|**Web cache deception**|Al revés: smugglea una petición para que el back-end sirva contenido sensible (de otro usuario) bajo una URL que la caché SÍ cachea (ej. `/my-account/nonexistent.js`)|Caché que decide cachear por extensión/patrón de ruta|

## 7. CL.0 (y H2.0) — cuando el back-end simplemente ignora el body

Aquí ya no hace falta tocar `Content-Length` ni `Transfer-Encoding` de forma "sucia": el `Content-Length` es completamente correcto y normal. El problema es que el **back-end** decide ignorarlo (asume que ese endpoint nunca tiene body, típico en redirects a nivel de servidor o recursos estáticos que reciben un `POST` por error).

### 7.1 Testeo directo

```http
POST /vulnerable-endpoint HTTP/1.1
Host: vulnerable-website.com
Connection: keep-alive
Content-Type: application/x-www-form-urlencoded
Content-Length: 34

GET /hopefully404 HTTP/1.1
Foo: xGET / HTTP/1.1
Host: vulnerable-website.com
```

En Burp Repeater: mete el "setup request" y un "follow-up request" cualquiera en un **group**, y envíalo con **"Send group in sequence (single connection)"**, con `Connection: keep-alive`. Si el follow-up (que debería dar 200) recibe un **404**, confirmado: el back-end trató el body del primer POST como el inicio de otro request.

### 7.2 Cómo "provocar" (elicit) el comportamiento CL.0 si no lo ves a la primera

- Prueba endpoints que normalmente no esperan `POST` (redirecciones a nivel de servidor, ficheros estáticos).
- Provoca un error de cabeceras (ej. header malformado) — algunos servidores devuelven el error **sin consumir el body** del socket, y si no cierran la conexión, ahí tienes tu desync.
- Prueba con `GET` + un `Content-Length` ofuscado (mismas técnicas de la tabla de §4) para esconderlo del back-end pero no del front-end.

### 7.3 Explotación

Exactamente **la misma tabla de la sección 6** (bypass de controles, captura de requests, XSS, cache poisoning/deception) — el resultado final es el mismo desync, solo cambia cómo lo consigues.

### 7.4 H2.0

Es el equivalente cuando hay downgrade HTTP/2 → HTTP/1 y el back-end ignora el `Content-Length` resultante del downgrade. Mismo concepto, mismo triage que H2.CL/H2.TE pero comprobando si el back-end "traga" sin mirar el body.

---

## 8. 0.CL — el front-end es el que ignora Content-Length

Menos común y más avanzado: aquí es el **front-end** el que ignora `Content-Length` y el back-end sí lo procesa. Durante años se consideró casi inexplotable porque genera un _deadlock_ entre servidores (ambos se quedan esperando datos que el otro no va a enviar).

La técnica moderna (ver whitepaper _"HTTP/1.1 Must Die"_ de PortSwigger) combina esto con un **"early-response gadget"** (forzar que el back-end responda antes de recibir el body completo) para romper el deadlock, y luego encadenar un **doble desync** para construir el exploit completo. Si te topas con esto en un mystery lab muy difícil, es la pista: busca un endpoint que responda "antes de tiempo" (redirects, errores) y combínalo con el patrón 0.CL.

## 9. Response queue poisoning (impacto máximo, cuando hay reuse de conexión)

Si ya confirmaste **cualquiera** de las variantes anteriores (clásica o vía H2), puedes escalar a esto: en vez de smugglear un _prefijo_ de request, smugglea un **request completo** que reciba una respuesta propia. Esto desincroniza la **cola de respuestas**: a partir de ahí, cada respuesta que llegue por esa conexión va desplazada una posición — tú (u otro atacante) puedes acabar recibiendo la respuesta que le correspondía a otro usuario (sesión, tokens, contenido privado…).

Ejemplo de patrón (HTTP/2 → downgrade, con TE):

```http
POST /x HTTP/2
Host: vulnerable-website.com
Transfer-Encoding: chunked

0

GET /x HTTP/1.1
Host: vulnerable-website.com

```

Usa una ruta que dé **404** a propósito como marcador — así reconoces fácilmente cuándo tu request "extra" ha entrado en la cola, y puedes ir haciendo peticiones normales para ir "desplazando" la cola hasta capturar la respuesta de otro usuario (ej. el panel de admin cuando un admin haga login).

**Qué explotar:** secuestro de sesiones/tokens de otros usuarios, bypass de autenticación completo, y en el peor caso, control total del sitio si logras capturar la respuesta de un panel administrativo.

---

## 10. HTTP request tunnelling — cuando NO hay reuse de conexión

Si el front-end abre una conexión nueva al back-end por cada request (sin _keep-alive_ entre servidores), los ataques "clásicos" de arriba no sirven porque dependen de que tu request quede pegado al de otro usuario en la misma conexión. Aun así, puedes:

- Meter un **request anidado completo dentro de tu propio request** (usando las mismas técnicas de longitud ambigua) para que el back-end vea _dos_ requests dentro de uno solo, aunque nunca se reutilice la conexión hacia otro usuario.
- Con esto puedes: filtrar cabeceras internas que el front-end añade (`X-Forwarded-For` reales, etc.), hacer _tunnelling_ ciego (blind) o no ciego usando `HEAD` para leer la respuesta del request interno, y encadenar hasta web cache poisoning.

Esto es más de "última milla" del temario avanzado — si te sale en un mystery lab, la pista suele ser: "confirmo desync con HTTP/2, pero el reuse de conexión no funciona" → piensa en tunnelling.

---

## 11. Client-side desync (variante que ataca al navegador de la víctima)

Estas usan un `Content-Length` **perfectamente válido y sin ofuscar** — el desync ocurre porque el **navegador de la víctima** reutiliza su propia conexión hacia el sitio de forma predecible. No necesitas herramientas tipo Burp para explotarlo en producción: se dispara con JS/fetch normal desde una página controlada por el atacante.

**Qué explotar:**

- Variantes "client-side" de los ataques clásicos (§6), pero contra la propia víctima en vez de contra otro usuario aleatorio.
- **Client-side cache poisoning**: forzar a la víctima a envenenar su propia caché local o una caché compartida vía redirect.
- **Pivote contra infraestructura interna**: si el navegador de la víctima tiene acceso a algo que tú no (VPN, red corporativa), puedes usar su conexión desincronizada como trampolín.

## 12. Chuleta rápida — árbol de decisión para el examen

```
¿Timing con payload CL.TE (Content-Length correcto, TE de más)?
 └─ SÍ → confirmar con differential response → CL.TE
 └─ NO → ¿Timing con payload TE.CL?
     └─ SÍ → confirmar → TE.CL
     └─ NO → ¿El sitio soporta HTTP/2 de cara al cliente?
         └─ SÍ → probar H2.CL y H2.TE (forzar protocolo H2 en Repeater)
         └─ NO/tampoco nada → probar variantes de ofuscación TE.TE
             └─ Nada de esto funciona → probar CL.0 (Content-Length normal,
                dos requests en secuencia, misma conexión)
                └─ Sigue sin salir pero hueles desync → 0.CL / early-response
                   gadget / request tunnelling (temario avanzado)
```

Una vez tengas el tipo confirmado, ve directo a la **tabla de la sección 6** (o 7.3 si es CL.0/H2.0) para decidir qué explotar: normalmente el enunciado del lab/mystery lab ya te dice el objetivo (bypass admin, robar respuesta de otro usuario, XSS, cache poisoning...), así que solo te falta encajar el _payload smuggleado_ correcto detrás del desync que ya confirmaste.

## 13. Notas sobre la extensión HTTP Request Smuggler

- Botón derecho sobre un request → **"Launch Smuggle probe"** → revisa la pestaña de output de la extensión.
- La versión 3.0 (2025) añade detección por discrepancias de parseo (root-cause), no solo por mismatch CL/TE, lo cual la hace más fiable contra defensas modernas.
- Detecta también: CL.TE/TE.CL con confirmación por timeout, smuggling en HTTP/2 (incluyendo tunnelling e inyección vía headers), desyncs client-side, smuggling/eliminación de headers, y manipulación de estado de conexión (pause-based).
- Úsala para **descubrir rápido** el candidato, pero para el examen BSCP practica también construyendo los payloads a mano en Repeater — el examen no siempre deja usar extensiones y, sobre todo, necesitas entender _por qué_ funciona cada uno para adaptarlo cuando el payload "de libro" no funcione tal cual contra el target.
